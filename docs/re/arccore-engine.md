## 1. Shape of the boundary

ArcCore is not a CEF-style C API. It is three layers:

1. **C entry points (8 exports).** From `nm -gU .re/bin/ArcCore-arm64` (259 exports total):
   `ChromeMain`, `ChromeAppModeStart_v8`, `ChromeWebAppShortcutCopierMain`, `SetLogMessageHandler`, `emitTraceEvent`, `arcCategoryEnabledFlag`, `CallWithEHFrame`, plus the `ArcErrorDomain` constant. `ChromeMain` is the standard Chromium framework entry: helpers and the browser process call it, and it runs the whole Chromium browser process. The main Swift app does **not** call `ChromeMain` as its UI entry; it links ArcCore (`otool -L` on `Contents/MacOS/Arc` shows `@executable_path/../Frameworks/ArcCore.framework/Versions/A/ArcCore`, version 8078.0.48) and drives Chromium in-process through the ObjC API below, with `ArcBrowserApplication run` / `initialize:` starting the browser process run loop.
2. **146 exported ObjC classes** (`nm -gU`, `OBJC_CLASS_$_Arc*`), each a thin wrapper over a C++ `arc::` object held as `std::shared_ptr<…::Impl>` (visible in every class's type encoding, e.g. `ArcBrowser.nativeBrowser :: {optional<arc::Browser>=…shared_ptr<arc::Browser::Impl>…}`). Identity is consistent: `initWith<Native>:` takes the C++ object by value/reference; value types also expose `mutable<Native>` / `init:<fields>:` constructors.
3. **C++ delegate bridges.** There are **no exported `Arc*` ObjC protocols** (`__objc_protolist` holds 69 protocols, all Apple/Chromium-internal: `NSObject`, `NSTextInputClient`, `RenderWidgetHostViewMacDelegate`, etc.). Instead, each `setDelegate:` / `setNavigationDelegate:` / `addObserver:` takes a plain ObjC object (`@`, e.g. `ArcWebContents setNavigationDelegate: :: v24@0:8@16`). ArcCore internally wraps it in a C++ `…DelegateBridge` (e.g. `ArcWebContentsNavigationDelegateBridge`, `BrowserContextExtensionsDelegateBridge`, from the property type encodings) and forwards C++ virtual calls to ObjC selectors on the Swift object. The selector contract is therefore implicit; §2 lists the selectors found in `__objc_methname` (7,009 selectors total; delegate selectors extracted in `.re/arccore/objc-selectors.txt`).

Consequence for Open: the Swift side (module `ADK` in the Arc app; strings `ADK/BrowserDelegate.swift`, `ADK/BrowserContextDelegateBridge.swift`, types `ADKBrowserDelegate`, `BrowserContextDelegateBridge`, … in `strings -a` on the Arc binary) implements informal ObjC delegate objects. The engine never references Swift types.

Which classes the Swift app statically references: `nm -u` on the Arc binary lists 367 undefined ObjC classes; only **63 of the 146** ArcCore classes intersect (`.re/arccore/arc-uses-core-classes.txt`). The other 83 (e.g. `ArcWebContents`, `ArcBrowser`, `ArcDownloadItem`) are never allocated by Swift; the engine creates them and hands them to Swift through delegate callbacks and return values. Any Open engine layer needs the same split: Swift allocates configuration/value objects; the engine allocates web contents, browsers, downloads.

Both helper families are stubs; all code lives in ArcCore:

- **Classic helpers** (166 KB) contain Chromium's seatbelt bootstrap: strings `Failed to create seatbelt sandbox server.`, `--seatbelt-client=`, `SeatbeltExec: %s %s failed`, imports `_sandbox_apply`, `_sandbox_init_with_parameters`, `_dlopen`, `_dlsym`, plus the literals `ChromeMain` and `../../../../ArcCore`. Flow: helper applies/serves its own sandbox, `dlopen`s ArcCore, jumps to `ChromeMain` with `--type=…` arguments.
- **Aperitif helpers** (99 KB) are 20 bytes of `__text` (`otool -l`: `__text` size `0x14`). They link **directly** against `@executable_path/../../../../Libraries/libaperitif.dylib` and `@executable_path/../../../../ArcCore` (`otool -L` on the thinned slice) and import only `_AperitifCheckInitialized`, `_ChromeMain`, `_exit`. Flow: the **browser process applies the seatbelt sandbox before `exec`** (the "aperitif" is served before the meal); the stub verifies the sandbox is already up, then calls `ChromeMain` in the already-linked framework. No `dlopen`, no sandbox code, no string table.
- `libaperitif.dylib` (166 KB fat, single export `_AperitifCheckInitialized`) holds the shared sandbox logic: strings `Failed to create seatbelt sandbox server`, `org.chromium.sandbox`, `SandboxSerializer: Failed to deserialize policy`, `--seatbelt-client=`. ArcCore selects the family with the feature string `kAperitifHelpers` and helper-name fragments `(Aperitif)`, `(Aperitif GPU)`, … in its string table. Which family runs by default cannot be determined from binaries alone (guess: Aperitif, since it is the newer Chromium macOS sandbox design and the classic set is kept as fallback).

Entitlements: helpers carry only `com.apple.security.cs.allow-jit` (renderer/GPU) or `com.apple.security.cs.disable-library-validation` (generic); the sandbox is seatbelt profiles passed at launch, not App Sandbox entitlements. ### 4.3 chrome.tabs / chrome.windows with a sidebar tab model

Arc does not use Chrome windows/tab strips as UI, yet `chrome.tabs` must work. The evidence for how:

1. Arc's `Browser` still tracks a Chromium tab model internally. Strings `Browser::OnTabStripModelChanged`, `WebContents::Impl::OnTabStripModelChanged`, and the full `chrome/browser/ui/tabs/tab_strip_model.cc` + `tabs_api.mojom.TabStripService` (`GetTabs`, `ActivateTab`, `CloseNodes`, `CreateTabAt`, `MoveNode`, `SetSelectedTabs`, `ReplaceTabInSplit`, …) are compiled in. The tab strip exists as a *model*, mirrored from Arc's own tab list, with no Views tab strip attached (guess, but the only consistent reading: extension APIs and session restore need a `TabStripModel`, so `arc/browser/browser_impl.cc` maintains one per `Browser`).
2. Stable identity crossing the boundary is Arc's **SessionID**, not a raw WebContents pointer: `ArcWebContents.sessionId`, `ArcSessionTab`, `browser:didCreateNewWebContents:isActive:`, tab-group bridge methods `browser:createTabGroupWithSessionIds:properties:completion:`, `addTabsToGroupWithId:sessionIds:…`, `updateTabGroupWithId:…`, `moveTabGroupWithId:toNewIndex:…`, `getAllTabGroupsWithCompletion:`, `extensionGroupIdForTabWithSessionId:` (types `ArcTabGroupInfo/Properties/Result`, `ArcSessionTabGroup`). So `chrome.tabs.group`/`tabGroups` are implemented by asking Swift to mutate Arc's real groups and mapping the result back to extension group IDs. `BrowserDelegate::GetExtensionGroupIdForTab`, `::CreateTabGroup`, `::AddTabsToGroup`, `::RemoveTabsFromGroup`, `::UpdateTabGroup`, `::MoveTabGroup`, `::GetAllTabGroups` (C++ strings).
3. Incognito maps to `ArcBrowserContextID.isIncognito`; extension windows map to `ArcBrowser` objects keyed by `windowIdentifier`.

**Required hooks for an embedder (the checklist Open must implement for extensions):**

- [ ] A per-profile extension service with list/enable/disable/reload/uninstall, Web Store + unpacked install, and lifecycle events (ready, installed, uninstalled, load-failed with manifest/runtime errors).
- [ ] An action model: engine produces immutable toolbar-action snapshots (id, title/tooltip, icon, badge-equivalent state via `enabled`, pinned position); UI renders them anywhere; clicks call back `executeExtensionAction`.
- [ ] A popup host: engine owns popup WebContents creation, sizing (`didResize…size:`) and teardown; UI supplies an `NSWindow`/panel and embeds the native view. Popup lifetime is engine-driven; the window must close when the engine says so (focus loss handled in engine).
- [ ] Pin order persistence + change notification; an extensions menu model (all actions, pinned subset, Manage Extensions / Get More Extensions entries — Chrome strings `ExtensionsMenuModel::kVisitChromeWebStoreMenuItem` remain).
- [ ] Consent UI callbacks for install, uninstall, and host/permission prompts, answered asynchronously via completions.
- [ ] A tab-model mirror: every Arc/Open tab (pinned, today, split-view member, Little Arc, Peek) needs a stable engine tab identity exposed to `chrome.tabs` (id, windowId, index, active, pinned, groupId, url/title/favicon/status, audible/muted), with create/remove/update/move/activate events. Split View is the hard case: two WebContents, one visual tab — Arc's `tabs_api.mojom.TabStripService.ReplaceTabInSplit` string suggests upstream Chromium 156 already models splits; Open must decide the mapping and document it.
- [ ] A window-model mirror: `chrome.windows` ↔ Open windows (main, Little Arc, popup browsers via `createPopupBrowser:withDelegate:`), with focus/ bounds events.
- [ ] Tab-group bridge both ways (extension-created groups must appear in the sidebar; sidebar groups must be visible to extensions). Open v1: no groups (§4.3.1).
- [ ] Omnibox keywords (`triggerExtensionOmniboxInput`), extension commands (global shortcuts), context menus (`showExtensionContextMenu:` + `ArcMenuModel`), side-panel hosting, devtools for extension pages (background/service-worker inspection via `ArcBrowserContextDevTools`), and error surfacing (`ArcExtensionRuntimeError`).

### 4.4 CEF gap

CEF exposes extension *loading* (`CefRequestContext::LoadExtension`, `CefExtensionHandler`) but has no supported equivalent of: toolbar-action state sync, popup WebContents hosting with resize callbacks, `chrome.tabs`/`chrome.windows` against a non-Chrome tab model, tab groups, side panel, Web Store install flow, or consent-prompt plumbing. ## 8. Risks for a CEF-based approach

1. **Extensions are the risk, not rendering.** §4.4: stock CEF cannot reproduce Arc's action/popup/tabs/windows/side-panel behaviour. Options: (a) patch CEF/ Chromium (`libcef` + Chrome-layer code) to add an `ExtensionsContainer`-equivalent and a tab-model mirror — real Chromium work, budget weeks and assign an owner; (b) ship CEF extensions in "load-only" mode (content scripts/background work, no popup UI parity) and accept reduced compatibility — violates the v1 "Chrome Web Store extensions must work" decision if users expect popups; (c) move to an own Chromium fork earlier than planned. Decide before building sidebar extension UI. Arc's design (engine-owned popup WebContents + Swift window) is the target shape whichever option is chosen.
2. **Widevine.** Arc ships Google Widevine (`com.google.widevine.alpha`). CEF does not include a redistributable Widevine CDM; Open needs its own Widevine licensee agreement or DRM sites (Netflix/Spotify) fail. Start the licensing process early; it is paperwork-latency-bound.
3. **No CEF equivalent of the delegate-bridge API.** Arc's 146-class ObjC surface is generated from C++ (`arc/browser/public/*`). With CEF, Open must write this layer by hand over `CefBrowser`, `CefFrame`, `CefRequestContext`, etc. Keep the §7 checklist as the spec; do not let CEF types leak into Swift (the engine-layer decision in `AGENTS.md` exists for this reason).
4. **Tab identity.** Arc's SessionID bridge (§4.3) exists because extensions, sessions and tab groups need stable IDs independent of view lifetime. CEF browser IDs are process-scoped integers; Open must mint its own stable tab IDs on day one and map bidirectionally. Split View and tab discarding (`discard`, freezing votes) make this easy to get wrong.
5. **Weight.** A CEF build is the same order of magnitude as ArcCore (~240 MB arm64 + ~40 MB resources after locale trimming). "Lightweight" gains come from locale trimming, arm64-only shipping, and not bundling AI models — not from the engine choice. Set a size budget and measure the first CEF integration against §6.
6. **Sandbox/helpers.** CEF helpers must be renamed, re-signed and entitlement-matched with the main app, or notifications, camera/mic TCC prompts and updates break. Arc's Aperitif work shows helper bootstrap is security-sensitive; do not customise CEF's helper sandboxing without a security review.
7. **Chromium version drift.** Arc is on Chromium 156 (branch 8078). CEF releases trail Chromium; extension API surface (MV3, side panel, tab groups) differs by version. Pin a CEF version, record its Chromium version next to this file, and re-run the §4.3 checklist against it.
8. **Dead-code trap.** ArcCore links large amounts of Chrome UI/sync code it never shows. When measuring CEF gaps, compare *behaviour* (§4.3, §7), not symbol presence: presence in the binary does not mean Arc uses it, and absence in CEF does not matter unless a checklist item needs it.
