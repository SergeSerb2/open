# Engine patch plan (our Chromium fork)

Status: plan, 2026-10-25. Base: Chromium 156.0.8078.48 with CEF branch 8078 at commit `4fa4ab516` (`~/Developer/open-engine/chromium_git/chromium/src`, `src/cef`). The pins live in `tools/fetch-cef.sh`.

This plan lists the changes that our fork needs on top of stock CEF, ordered by value. Each item names the source files that prove the gap and the files the patch touches. All paths are relative to `chromium/src`. The evidence comes from reading that tree and from the end-to-end runs in [engine-spike.md](engine-spike.md). Effort numbers are estimates for one engineer who knows Chromium; they are guesses, not measurements.

## How the patches are stored

The fork layout is owned by [docs/plans/fork-infra.md](plans/fork-infra.md) and [docs/engine-fork.md](engine-fork.md): pins in `Engine/fork/VERSIONS`, hook patches in `Engine/fork/patches/{cef,chromium}/` with a `series` (apply order) and a `manifest` (paths per patch), and new files in the overlay `Engine/fork/src/`, which mirrors `chromium/src/`. `Engine/fork/scripts/engine-apply` applies CEF's own patches first, then Open's series, then the overlay.

For this plan:

- New engine code goes in the overlay: `Engine/fork/src/cef/libcef/browser/chrome/open/` for the CEF-side classes below and `Engine/fork/src/cef/include/` for new public headers. Existing files get small hook patches only.
- Series numbers: `03xx` for the extension work (P1–P3). Other plans already use `00xx` (ad blocking, [plans/adblock-fork.md](plans/adblock-fork.md)) and `01xx` (tab sleeping, [plans/memory-fork.md](plans/memory-fork.md)).
- New CEF API follows those plans' rules: guarded with `CEF_API_ADDED(CEF_API_VERSION_EXPERIMENTAL)`, C API regenerated by `cef/tools/translator.py`, never hand-edited (adblock-fork F-12, memory-fork F-18).
- The shell does not change when the patches land: the OpenEngine API in [engine-api.md](engine-api.md) already has the shape that these patches fill in (`OEBrowser`, `OEExtensionAction`, the popup delegate calls).
- The app builds against the fork by default (`tools/fetch-cef.sh`, `CEF_SOURCE=fork`), which runs `tools/fetch-engine.sh --run`. `CEF_SOURCE=cdn` selects stock CEF for comparisons.

## Summary

### E11/E12 and tab event follow-ups (2026-11-05)

The E11 window hook is `chromium/0306-open-extension-windows-tabs.patch`.
It owns `tabs_api.cc`; that file's P1 move/discard guards moved out of 0303
to keep patch manifests disjoint. 0303 still owns the lifecycle-unit discard
guard. New behavior lives in the overlay, not in generated C API files.

`OpenTabStrip::CreateExtensionWindow` makes a hidden `TYPE_POPUP` Browser,
with its own strip and hosted page. `OEBrowser` adopts it, then calls the
engine delegate outside the model observer stack. The App hosts that page in
`ExtensionWindowController`, a standard titled, closable, miniaturizable,
resizable window with no toolbar or sidebar. Explicit frames take priority;
otherwise AppKit restores `ExtensionPopupWindow`, or the App centers a 400×600
frame on its parent. Window bounds/focus come from the actual native window.
Normal windows requested by an extension become selected Today tabs in the
active Open window of the profile, retaining that window's id (guess (lead)).
Popup requests with multiple URLs are refused: this native surface hosts one
page (guess (child)). Sized page `window.open` panels and Peek action Q4 remain
separate follow-ups.

`CefOpenOmnibox` uses Chromium's `ExtensionOmniboxEventRouter` and
`OmniboxSuggestionsWatcher`, with enabled-keyword and profile guards. It sends
start/change/enter/cancel/delete events, reads Chromium's parsed default
suggestion, and reports default changes. Negative process-wide request ids
stay separate from Chromium's positive autocomplete ids. Only the first
reply to the latest text is delivered. The App bridges cancellation and
supersession to nil async replies and provides enabled actions, keyword
scopes, icons, and Cocoa shortcut keycaps to the command bar. Default refresh
reuses the current reply and sends no extra input event.

The minimal sidebar-to-Chromium event mapping is:

| Open change | Equivalent strip change and extension event |
|---|---|
| Reorder within a Space | Move the live tab to its new flattened index; native `tabs.onMoved`. |
| Move to another Space in the same profile | Move to the new flattened index, retaining tab/window ids; native `onMoved`. A Space change that leaves the strip index unchanged has no Chrome equivalent event. |
| Pin/unpin | Change Chrome's pinned state and its required strip position; native `onUpdated({pinned})` and any corresponding `onMoved`. Favorites remain pinned. |
| Focus another Split View pane | Activate and single-highlight the focused pane; native `onActivated` and `onHighlighted`. Other visible panes remain background strip tabs. |
| Extension `tabs.update({pinned})` | Request the model's pin/unpin operation, then mirror the result. Favorites stay Favorites. |

No synthetic duplicate events are sent. Array `tabs.move` requests capture
neighbour WebContents in the observer, before later moves or shell syncs can
change the model; the deferred bridge resolves those neighbours by identity.

The real-App acceptance suite is `--only extensions-e2`; P3, actions,
extensions, tabstrip and the shell regressions remain separate gates.

## P1. Tab-strip bridge (highest value)

### The gap

1. Stock CEF on macOS cannot host a Chrome-style browser in our NSView. `cef/libcef/browser/chrome/views/chrome_child_window.cc:26-33` returns a null parent on macOS ("Chrome style is not supported with native parent on MacOS. See issue #3294"). `cef/include/internal/cef_types_mac.h:151-152`: "Alloy style will always be used ... if |parent_view| is provided."
2. Alloy-style web contents (the only kind that goes into our NSView) are in no Chrome `Browser`, so the extension tab APIs cannot find them. Measured: `chrome.windows.getCurrent()` from an action popup fails with "No current window", and `chrome.tabs.query({})` returns `[]` (results-extensions-alloy.json, `popups.*.tabs_api`).
3. Chrome-style web contents in stock CEF each get their own Views-hosted `Browser` window with one tab. `cef/libcef/browser/chrome/chrome_browser_host_impl.cc:102`: "Views-hosted Browsers will contain a single ChromeBrowserHostImpl." Measured: with 3 sidebar tabs plus a popup, `chrome.windows.getAll()` returns 4 windows, and the popup sees itself as the active tab (results-extensions-chrome.json).
4. In 156 the tab APIs run over `TabListInterface` (`chrome/browser/tab_list/tab_list_interface.h:40-54`; `tabs_api.cc` uses it 30 times and `TabStripModel` once), attached as user data to a `BrowserWindowInterface`. Windows reach extensions through `extensions::BrowserExtensionWindowController(BrowserWindowInterface*)` (`chrome/browser/extensions/browser_extension_window_controller.h:26-30`). On desktop, though, `BrowserWindowInterface::GetTabStripModel()` is a pure virtual (`chrome/browser/ui/browser_window/public/browser_window_interface.h:249`) that much desktop code calls. So a desktop window must still be a real `Browser` with a `TabStripModel`. (Arc does the same: ArcCore keeps `Browser::OnTabStripModelChanged` and the full `tab_strip_model.cc`; see docs/re/arccore-engine.md §4.3.)

### The patch

Keep one hidden Chrome `Browser` (with a real `TabStripModel`) per `OEBrowser`, and host each of its tabs' WebContents views in our NSViews.

1. **Headless `BrowserWindow` for macOS** (new `cef/libcef/browser/chrome/headless_browser_window.{h,mm}`). Implements `BrowserWindow` (74 pure virtuals in `chrome/browser/ui/browser_window.h`) with no Views widget. Template: `chrome/test/base/test_browser_window.{h,cc}` (693 lines of mostly no-op overrides). `GetNativeWindow()` returns the shell's NSWindow (passed in), `GetBounds()`/`IsActive()`/`Activate()` forward to it, `GetWebContentsModalDialogHostForWindow()` anchors dialogs (install prompt, auth) to the shell window.
2. **Chrome-style tabs with a native parent on macOS.** In `cef/libcef/browser/browser_host_create.cc` and `chrome_browser_host_impl.cc` (`CreateBrowser`, around line 405), when `window_info.parent_view` is set together with a new field `window_info.tab_strip_id`, create (or reuse) the hidden `Browser` for that id with `BrowserWindowCreateParams.window = <headless window>` and `TYPE_NORMAL`, and add the tab with `chrome::AddTabAt`. CEF already supports many `ChromeBrowserHostImpl` per `Browser` (`chrome_browser_host_impl.cc:100-104`). A new `CefBrowserPlatformDelegateChromeNativeMac` puts the tab's `WebContents::GetNativeView()` into `parent_view`, the way `cef/libcef/browser/native/browser_platform_delegate_native_mac.mm` does for Alloy.
3. **New CEF API** (`cef/include/cef_tab_strip.h`, new):
   - `CefTabStrip` (one per `OEBrowser`): `Create(request_context, native_window)`, `GetId()`, `SetActive(browser)`, `Move(browser, index)`, `SetPinned(browser, bool)`, `SetSplit(browsers[])`, `Close()`.
   - `CefTabStripHandler` (engine to shell, for changes that Chromium starts): `OnTabCreated(strip, browser, disposition)` for `chrome.tabs.create`, extension welcome pages, and `openOptionsPage`; `OnActivateRequested`, `OnMoveRequested`, `OnCloseRequested`, `OnPinRequested`, `OnGroupRequested(tabs, title, color)` for `chrome.tabs.update/move/remove/group` and `chrome.tabGroups`.
   - The shell stays the owner of order and grouping: Chromium asks, the shell decides and calls back.
4. **Default-client fallback goes away.** Today `OEDefaultClient` (`Engine/OpenEngine/src/OEEngine.mm`) catches Chrome windows that extensions open and reloads their URL in a new Open tab, which loses the tab's extension identity and `window.opener`. With P1, `Browser::AddNewContents` (CEF's `ChromeBrowserDelegate::AddNewContents`, `cef/libcef/browser/chrome/chrome_browser_delegate.cc`) adds the WebContents to the hidden tab strip and calls `OnTabCreated`.
5. **Split View** maps to Chromium 156's split tabs (`TabListInterface::CreateSplit`, `ListSplits`; `tab_list_interface.h:156-174`), so extensions see one tab per pane as Chrome does. Folders and Spaces are not tab groups (decision for the lead, see below).

OpenEngine side: `OEBrowser` creates the `CefTabStrip`; `-insertWebContent:atIndex:`, `-moveWebContent:toIndex:`, `-setPinned:forWebContent:`, and `activeWebContent` already exist and are kept exact by the shell (verified: `tab_strip_mirror` in results-shell-debug.json). `OEWebContent` creates its browser with `tab_strip_id` once P1 lands.

Risk: desktop `Browser` code expects a Views `BrowserView` in places (`BrowserView::GetBrowserViewForBrowser`). Each such call needs a null check; CEF's `chrome_browser_browser.patch` and `chrome_runtime_views.patch` already handle several of them for its Views-hosted case.

Deviations from the plan:

- No `window_info.tab_strip_id`: the shell creates hosted tabs with `CefTabStrip::CreateTab` (synchronous; `OnAfterCreated` runs inside), so `cef_window_info_t` keeps its ABI. Overlay code lives under `//open/` (lead decision) and is compiled into `libcef_static`.
- The hidden Browser exists only while it has tabs. `UnloadController::TabStripEmpty` puts an empty Browser into "unload completed", so it cannot take new tabs; Chrome closes it, and the strip makes a new one (new `chrome.windows` id) for the next tab.
- Extension action popups stay Alloy pages until P2: a Chrome style popup would get its own Views window. They still see the right window: a page outside any Browser gets the profile's most recently active Browser as its current window (`ChromeExtensionFunctionDetails::GetCurrentWindowController`).
- Sized `window.open` popups of a hosted tab are tabs of the opener's window in `chrome.tabs` (the shell shows them in a panel). Chrome would make them a separate popup window.
- Badge text and color, title, and enabled (part of P2) came along: `browserDidUpdateExtensionActions` fires on `chrome.action` changes.
- Found on the way: `OEEngineConfiguration.userAgentProduct = "Open/0.1"` replaced Chrome's `Chrome/156` UA token, and Bitwarden (like many sites) took its Safari code path and never loaded. The shell no longer sets it.

Window activation lifecycle (2026-11-06, X-19 / #192): `OpenBrowserWindow`
stops its NSWindow key observers when real closing starts and when the Browser
reports its close. A close request that the embedder can refuse keeps its
observers. Activation requires a Browser that is still registered in
`GlobalBrowserCollection`; this also covers `SetBrowser` and `SetHostView`.
Chromium's collection checks stay intact. The automation-only diagnostic
counts and refuses an unsafe activation before that check, so the real-App
`window` row `engine_close_host_activation` can prove the old behavior fails
without ending the App. The row includes immediate focus after a Profile
switch, then closes twice and changes native key state before deferred deletion.

Review round 1 (PR #53; engine review by Opus, shell review by Muse; lead decisions 2026-10-26):

- **Discards.** Chrome never discards a hosted tab: Open sleeps tabs itself. `chrome.tabs.discard(tabId)` becomes a request (`OnTabDiscardRequested` → `-browser:requestsDiscardOfWebContent:`). The shell refuses the visible tab (Chrome's "Cannot discard tab" error). The current App uses `SleepController.debugSleepNow`: it discards a background renderer and keeps the sleeping page and its tab id until a later destroy deadline. `OEWebContent.isDiscarded` reports that renderer state. Desktop `chrome.tabs` still reports `discarded: false` because Chrome's own lifecycle unit did not perform the discard; this metadata mapping remains a P1 follow-up. The tab leaves `chrome.tabs` only when the page closes. `chrome.tabs.discard()` without an id finds nothing to discard. A replaced `WebContents` (only discards replace one) is logged, never reported as a page close.
- **Windows own their tabs.** `tabs.move` to or from another window, `tabs.group` into another window, and `windows.create({tabId})` fail with "Tabs cannot be moved between windows in this browser." A hosted tab that still leaves its window by another path is put back. `-[OEBrowser insertWebContent:atIndex:]` refuses a page of another profile or another hidden window.
- **`chrome.windows.remove`** on an Open window with tabs becomes `OnCloseRequested` → `-browserRequestsClose:`; v1 refuses and logs it, and the extension's call still resolves. "Last tab gone" and the shell's own `-close` close for real; `-close` marks the window's pages closing first, so they are not reported as page closes.
- **Non-default profiles.** Round 1 refused a tab strip for a context whose disk profile CEF could not create (it fell back to an off-the-record profile of the default profile, whose incognito-allowed extensions could see its tabs). The profile layout fix (`<root>/Engine/<dir>`, a direct child of `root_cache_path`) gives every profile a real disk profile. `OEEngine` now refuses (nil) a context folder that is not a direct child of the root, and the guard stays as a backstop (`LOG(ERROR)`) for a CEF failure of any other kind (engine review r1, 88-3). e2e `--only profiles`: `extension_isolation` (the default profile's probe allowed in incognito sees no Work tab, in both directions) and `disk_profiles_on_disk` (each profile has its own `Preferences`, a `Local State` entry, and a Chrome window).
- **`CreateTab`** inserts its own `WebContents` into its own Browser (an off-the-record profile's `Navigate()` sends `chrome://settings` and similar to another window) and keys the pending client by that `WebContents`.
- **Action state** (badge, title, enabled) is reported after Chromium's active tab matches the shell's selection, not one switch later.
- **Context menus.** Every Chrome context-menu command runs in a hosted tab without a crash (e2e `context_menu_commands`: 57 commands on page, link, image, video, selection and editable targets). Fixed on the way: the toast and QR code crashes above; Writing Direction (CEF 0303); and DevTools opened by Inspect got the inspected page's CEF client, so closing DevTools closed the tab (`OEClient` now gives DevTools its own client in `OnBeforeDevToolsPopup` and ignores callbacks for other browsers). Not run: Emoji & Symbols, Speech, Services and Show Spelling and Grammar, which only open system UI (titles are matched by letters only, since AppKit drops the "&").
- **Shell rules** (port in `App/WebContent/EngineWebContentHostFactory.swift`): `TabStripMirror` is the only owner of strip order (favorites, every Space's pinned tabs, then every Space's Today tabs); requests change OpenModel and resync. A Favorite's pin and unpin are no-ops. `chrome.tabs.remove` and `window.close()` follow Cmd-W: pinned tabs and Favorites unload in place, Today tabs close (archived). `chrome.tabs.move` is applied only when one position in the tab's own parent puts it between the same two strip tabs; anything else (into a folder or split, across sections or Spaces) is refused and resynced. Peek pages are Alloy and never tabs.

Review round 2 (Opus re-check; lead decisions 2026-10-26):

- **New windows.** "Open Link in New Window" and Shift-click from a hosted tab no longer make the page a tab of the opener window's hidden Chrome window (it died with that window). The shell answers the engine's request with nil and opens the URL as a new tab of the new window. ## P2. Extension actions and popups for our UI

### The gap

- CEF exposes no action model. OpenEngine reads the installed set from `Preferences`/`Secure Preferences` and each `manifest.json` (`Engine/OpenEngine/src/OEExtensions.mm`). So title, icon, and popup are the manifest defaults; `chrome.action.setBadgeText/setIcon/setTitle/setPopup` and per-tab state never reach our UI, and `badgeText` is always nil.
- A click on a popup-less action must fire `chrome.action.onClicked`; stock CEF cannot (`-[OEBrowser executeExtensionAction:]` returns NO).
- Our popup is a plain page loaded with the popup URL. It renders and runs (uBO Lite, Dark Reader, 1Password: results-extensions-alloy.json), but Chromium does not treat it as a popup: `chrome.extension.getViews({type: "popup"})` does not include it, `chrome.tabs.query({active: true, currentWindow: true})` does not return the page under it, and Bitwarden's popup never leaves its loading spinner in Alloy style (screenshot `alloy-popup-bitwarden.png`; guess: it waits on the tab query).

### The patch

Chromium 156 already splits the action logic from the Views UI, and has two non-Views users to copy:

- Model: `ToolbarActionsModel` (`chrome/browser/ui/toolbar/toolbar_actions_model.h:44`) with `Observer::OnToolbarActionAdded/Removed/Updated/PinnedActionsChanged` (lines 82-100), `MovePinnedAction` (147), `pinned_action_ids()` (150).
- Per action: `ExtensionActionViewModel` (`chrome/browser/ui/extensions/extension_action_view_model.h:55`): `GetIcon(web_contents, size)`, `GetActionTitle`, `GetTooltip`, `IsEnabled`, `ExecuteUserAction(InvocationSource)`, `TriggerPopupForAPI`, `GetContextMenu`.
- Popup handoff: `ExtensionActionDelegate::TriggerPopup(std::unique_ptr<ExtensionViewHost> host, ...)` (`chrome/browser/ui/extensions/extension_action_delegate.h:63`). The model creates the host with `ExtensionViewHostFactory::CreatePopupHost(extension, url, BrowserWindowInterface*)` (`chrome/browser/extensions/extension_view_host_factory.h:37`), which is why P2 needs P1's window.
- Container: `ExtensionsContainer` is user data on the window (`chrome/browser/ui/extensions/extensions_container.h:27`).
- Templates: `chrome/browser/ui/webui/webui_toolbar/webui_toolbar_extensions_container.{h,cc}` (a toolbar that pushes action state to a page and gets `ExecuteUserAction` back, the same job as our bridge) and the Android files `chrome/browser/ui/android/extensions/extension_action_delegate_android.{h,cc}`, `extensions_toolbar_android.cc:81-93`, `extension_action_popup_contents.{h,cc}` (hosts an `ExtensionViewHost` without Views: implements `ExtensionView::ResizeDueToAutoResize`, close handling, devtools inspect).

New code: `cef/libcef/browser/chrome/extensions/cef_extensions_container.{h,cc}` (an `ExtensionsContainer` + `ToolbarActionsModel::Observer` on the hidden `Browser`), `cef_extension_action_delegate.{h,cc}` (an `ExtensionActionDelegate`), `cef_extension_popup_host.{h,mm}` (port of `ExtensionActionPopupContents` that puts the host's WebContents view into an NSView).

New CEF API (`cef/include/cef_extension_action.h`):

- `CefExtensionActionInfo`: id, name, title, tooltip, icon (`CefImage` for the active tab), badge text, badge colors, enabled, has popup, pinned index.
- `CefTabStrip::GetExtensionActions()`, `ExecuteExtensionAction(id)`, `PinExtensionAction(id, index)`, `ShowExtensionActionContextMenu(id)`.
- `CefExtensionActionHandler`: `OnActionsChanged(strip)`, `OnPopupOpened(strip, popup_browser, extension_id)` (the popup is a `CefBrowser`, so OpenEngine wraps it in an `OEWebContent` like any page), `OnPopupResized(strip, size)`, `OnPopupClosed(strip)`.

OpenEngine side: no API change. `OEExtensionAction` gets live values, `-browserDidUpdateExtensionActions:` fires on updates, and the popup delegate calls (`didOpenExtensionPopup`, `didResizeExtensionPopup`, `didCloseExtensionPopup`) carry the real host.

Decisions and limits (Section 3):

- **Natural size, not CSS area.** The browser does not know element rects, so `largestVideoSize` and the PiP choice use the largest natural area among playing videos (ties: the one that started last). The plan's §4.5.3 asked for the largest visible CSS area; a small element that shows a large video wins over a large element that upscales a small one. The App's A2 floor (160×90) now reads video pixels.
- **`disablePictureInPicture` in the browser.** The browser-initiated path (`MediaPlayer::RequestEnterPictureInPicture` → `HTMLVideoElement::RequestEnterPictureInPicture` → `PictureInPictureControllerImpl::EnterPictureInPicture`) checks neither user activation nor `IsElementAllowed` (`third_party/blink/renderer/modules/document_picture_in_picture/picture_in_picture_controller_impl.cc`), so `RequestPictureInPicture` refuses a video whose own availability report is false (Blink `SupportsPictureInPicture` = `IsElementAllowed == kEnabled`, sent on first play, on `loadeddata` and on attribute changes, `html_video_element.cc`). The largest playing video is the candidate; if it is disabled, the request fails (no fallback to a smaller video).
- **Muted tabs.** Chromium leaves a muted tab's players out of its media session (`MediaSessionController::IsMediaSessionNeeded`: `has_audio_ && !web_contents_->IsAudioMuted()`), so the session part keeps its last unmuted value while the tab is muted (the mini player stays), and play, pause and seeks go to the players. A tab muted before its first playback never gets a controllable session (no mini player) until it is unmuted. Previous/next track and meeting actions do nothing in a muted tab.
- **MediaStream players** (`srcObject` streams, `WebMediaPlayerMS`) are "one shot" content (`third_party/blink/renderer/modules/mediastream/web_media_player_ms.cc`), so they are never controllable; their playback, video and PiP still come from the players.
- **Tab volume and Web Audio.** The volume reaches media elements only (session players). Web Audio (`AudioContext`) is not a session player and plays at full volume; mute covers it.
- **PiP completion.** Chromium has no reply for a browser-initiated request: OpenEngine completes YES on the next `pictureInPicture` state, NO after 2 s (guess at the timeout).
- **Stock CEF fallback removed.** OpenEngine already includes `include/cef_tab_strip.h` unconditionally (`OEInternal.h`), so a `CEF_SOURCE=cdn` build cannot compile OpenEngine at all; a probe kept only for it would be dead code.

**Untrusted input.** Filter lists (EasyList, EasyPrivacy and the 46-list catalog) are untrusted network input. The engine parses them in the browser process (`FilterSet::add_filter_list`, `Engine::from_filter_set`), and it reads the serialized engine (DAT) back from disk (`Engine::deserialize`). The limits that exist today, in the Swift store (docs/adblock-lists.md):
- A source is capped at 16 MiB, and a combined list at 64 MiB. The cap is enforced while streaming, and the advertised size is checked.
- Downloads are HTTPS only. Redirects stay on the source host unless the catalog allows the destination.
- Each list generation has SHA-256 receipts. They are verified before every load, and a mismatch causes a fresh fetch.
- Bundled seeds are pinned by SHA-256 (`tools/fetch-adblock-lists.sh`, also `--max-filesize 16 MiB`).
- The engine is given only verified generation files, read with a size bound.

The parsers are memory-safe Rust apart from the `unsafe` crates listed above. A crate call that returns a `Result` can still panic on hostile input, and a panic ends the browser process (`-Cpanic=abort`): `Engine::deserialize` panicked on a DAT of 4 bytes (review 98-3), and `rmp-serde` resizes a buffer to a stream-controlled length of up to 4 GiB before it reads the bytes (`decode.rs:870`): a 14-byte DAT allocated 512 MiB (review R2-1), and an allocation failure aborts too; PartitionAlloc aborts on any single request over 2^31 − 2 MiB (2,145,386,496 B). The shim now walks every DAT before the crate reads it (`check_dat` in `lib.rs`): the crate's magic and version 0, then one MessagePack value whose every str, bin and ext length and every array and map count fits in the bytes left, at most 2^24 values and 32 levels, and nothing after it. A str or bin buffer can then be no larger than the DAT (at most 256 MiB, the service's read limit). A decoded collection is not bounded by the DAT's size: one DAT byte can become a 24-byte `String`, and at 2^27 values a 42.7 MiB DAT made one `Vec<String>` request 2,147,450,880 B and aborted the dev build (review R3-1). The value cap bounds collections: at 2^24 values the largest single requests measured are 536,862,720 B (`Vec<String>`) and 822,083,592 B (`HashMap<String, Vec<String>>`, heap peak 1.3 GiB), both under the ceiling. List text has its own limits before parsing (`check_build_limits`, review R3-2): at most 2^21 list lines across a build (today 132,043), and at most 64 MiB of cosmetic selector copies (the crate stores a selector once per hostname; today 596,174 bytes). A 16 MiB list of 5,592,405 two-character rules and a 149 KB line with 10,000 hostnames each aborted the dev build before; both are now refused with a reason, and the load fails. The self-test refuses the review's crafted DATs and lists with resident memory flat, and checks each limit at its boundary. The DAT receipt proves integrity at rest only: a same-user writer can forge a matching DAT and receipt, which the threat model accepts. Follow-up (`docs/followups.md`): fuzz list parsing, resources parsing and DAT deserialization, and add a parse time limit, before the first public release. adblock, regex, aho-corasick, the psl crate's embedded Public Suffix List data, and three RustSec advisories (`idna` 0.2.3 RUSTSEC-2024-0421, `rmp-serde` 0.15.5 RUSTSEC-2022-0092, `paste` 1.0.15 RUSTSEC-2024-0436; impact notes in docs/release/licenses.md) are on the release license and security review list (U-6).

- **Free functions in overlay headers instead of `CefBrowserHost` methods; no 0102/0103/0106 patch files.** `engine-refresh-patches` captures one `git diff HEAD` per patch over its manifest paths, so two patches can never share a file (docs/engine-fork.md: "Paths for different logical patches must not overlap"). - **Freeze state lives in a `WebContentsUserData`** (`PageLifecycleState`, overlay) instead of a `page_frozen_` member on `CefBrowserHostBase` (D-4's reason holds: content has no getter). - **Restore checks for an unused controller, not `GetEntryCount() == 0`.** A fresh `NavigationController` always holds the initial NavigationEntry, so the plan's check would refuse every restore. ## Profiles (Section 10, 0701–0703)

The Profile APIs use the experimental surface in overlay header
`cef/include/cef_open_profile.h`. `engine-apply` generates the C API, wrappers
and hashes. Swift calls only OpenEngine. New implementation lives in
`open/browser/profiles/open_profile_context.{h,cc}` and is compiled through
`open/open_libcef_sources.gni`; neither `cef/BUILD.gn` nor 0310's files gain
another manifest owner.

OpenEngine pins Chromium startup to `--profile-directory=Default`. On macOS,
`GetStartupProfilePath` otherwise selects `ProfileManager::GetLastUsedProfileDir`
(`chrome/browser/ui/startup/startup_browser_creator.cc:1756`), and CEF retains
that initial Profile as its global request context
(`cef/libcef/browser/chrome/chrome_browser_main_extra_parts_cef.cc:40–55`). A
named Profile used before quit must not become the process context on relaunch:
that would mix Default storage and keep the named Profile alive at deletion.
Named Profiles still load lazily through their own request contexts.

| Number | Change and reason | Files | Risk |
|---|---|---|---|
| 0701 | Chosen-parent primary OTR; observe native closure before CEF detaches it, and let a retained CEF wrapper report unavailable. Normal last-Browser cleanup stays with Chrome's ProfileDestroyer. A session released before its first Browser also goes through ProfileDestroyer. | `cef/0701-open-profile-lifecycle.patch`: `chrome/chrome_browser_context.cc`, `request_context_impl.h`; profile overlay and `cef_open_profile.h` | Primary OTR initializes before CEF adopts it. Native teardown can precede the shell's retained wrappers; they must become inert before another request. |
| 0702 | Ordered deletion coordinator in the overlay: real `WIPE_PROFILE` completion, `OnStoreDeletionFromDisk`, release CEF, independent late destructor sentinel, then remove/commit Local State. The macOS probe passed with automatic unload; no ProfileManager hook is needed. Keep-alives are never force-cleared. | Profile overlay, OpenEngine context/engine lifecycle code | Keep-alives, downloads, workers or delayed IO can block teardown. Specific errors preserve folders and the App's crash/retry cleanup remains necessary. |
| 0703 | Per-Profile browsing-data removal with completion, from begin through end, inclusive (Chromium semantics). This needs no upstream hunk: the public BrowsingDataRemover is reachable from the overlay. | Profile overlay, `cef_open_profile.h`, `OEBrowserContext.{h,mm}`, `AppSettingsActions.swift` | Storage backends use their own creation/modification timestamps; localStorage uses an origin's modification time. Open HistoryStore is separate. |

`makeIncognitoContext(for:completion:)` shares one private session per regular
parent, rejects unavailable/OTR/closing/policy-disabled parents, and never seeds
cookies or falls back to Default. The primary OTR retains Chrome's extension
opt-in and spanning/split behavior. This is an Open design choice; Arc's exact
parent selection is not established by the static research.

`deleteContext(_:completion:)` coalesces requests and retires the directory in
the running process. It closes private children, Browsers, pages, popups and
downloads before native deletion. The independent observer and late
`SupportsUserData` sentinel distinguish CEF wrapper detachment from actual
Profile destruction. The error diagnostics contain keep-alive origin numbers
and counts, with no profile name or path. Only success permits the App to remove
the Engine, cache and Open-store folders.

Quit tracks wrappers independently of the disk-context registry and invalidates
all managers/handles before `CefShutdown`, including the three-second deadline
path. Retained Swift objects stay closed. The App automation command
`profile-engine` provides native proof windows without introducing a second
product incognito or teardown implementation. The `profiles` e2e suite includes
the profile-engine flows; `--only profiles-engine` runs that portion alone.
