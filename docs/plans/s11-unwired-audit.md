## Coverage and negative findings

All **194 registry commands (185 active, 9 reserved)** were cross-checked against App dispatch, native selectors, PageTools and OpenFeatures dispatch. Registry declarations alone do not prove implementation. The unconditional App guard rejects these 13 active IDs: `new-incognito-window`, `new-profile`, `new-boost`, `edit-boost`, `new-legacy-boost`, `boost-gallery`, `cast`, `exit-modal`, `edit-theme`, `peek-email`, `join-meeting`, `manage-passwords`, `show-shortcuts-overlay`. Clear Cache has its own hard false gate. The remaining findings above are stubs, partial surfaces or explicitly labeled GUESS cases.

`EngineWebContentHostFactory.performSidebar` explicitly refuses seven intents: `showSiteControls`, `changeSpaceIcon`, `editSpaceTheme`, `newProfile`, `shareSpace`, `changeIcon`, `customizePage`. Its `default: return nil` at line 537 means **defer**, not refusal. `BrowserWindowController.swift:947`–993 handles the UI/split/confirmation intents; its default reaches `OpenSidebar/ModelSidebarActions.swift:19`–162. All remaining `SidebarIntent` cases have a handler along this chain. In particular:

- `exportSpaceIntoFolder`, `newNestedFolder`, node/bulk moves, pin/unpin, duplicate selections, rename, folder expansion, split separation/orientation, profile assignment and Space order reach model actions. They are not unwired.
- `manageSpaces`, `copyAllLinks`, `share`, `moveToNewSpace`, `moveNodesToNewSpace`, `turnFolderIntoSpace`, and `editPinnedURL` have real App paths at factory lines 505–533. The New Space flow upgrade remains section 4's work, as listed above.
- `setToolbarShown`, `sidebarHiddenByGesture`, `hoverPreview` and split additions reach OpenFeatures. `sidebarHiddenByGesture` and `hoverPreview` are notifications, not missing menu entries.
- All `MediaIntent` variants reach `App/Media/MediaCoordinator.swift:222`–252. `toggleVolumeDrawer` intentionally returns true because drawer presentation is view-owned; it is not an unimplemented engine action.
- All `CommandBarIntent` variants have a case at `App/CommandBar/AppCommandBarDelegate.swift:98`–126: open/search navigate, switch selects a model tab, runAction goes through the same controller dispatch, copy writes the pasteboard, search settings opens the Profile settings, and dismissed is a lifecycle notification. Action validation at line 42 uses the same App enablement gate. Unsupported actions are filtered; no second independent handler supplies missing behavior. `keyboard-shortcuts` and `reveal-tab-in-sidebar` are aliases, not gaps (`App/MainMenu.swift:47`). `focus-space` is dynamic and handled with its Space payload.
- Native menu commands use nil-target AppKit responder dispatch (`Packages/OpenKit/Sources/OpenCommands/MenuBuilder.swift:437`–492). This includes text editing, spelling, substitutions, transformations, speech, fonts, app/window controls and Find. Conditional disablement when no responder supports an action is expected; source inspection cannot prove every Chromium text-editing capability. The two Find fallback questions above are explicitly UNVERIFIED. Find/Next/Previous/Use Selection have concrete App handlers at factory lines 1604–1629 and are not general missing commands.
- `App/MainMenu.swift:80`–125 records normal contextual disablement: no selected page/tab, wrong pin/favorite state, no focused Space, fewer Spaces, no navigation history, no folder in the requested state, no changed pinned URL, sheet/menu already open, or invalid dynamic payload. Split actions require a split/capacity; record/cancel trace require the appropriate engine/tracing state. These state guards do not add missing features or change their existing owners.
- The Library manager has explicit surface restrictions (`App/Settings/AppSettingsActions.swift:75`–110): no browser navigation/chrome commands there; pinned unload refuses without a live browser. They prevent unsupported manager actions and do not mean standard-window sidebar intents are unwired.
- Find bar, JavaScript dialogs, permissions, page context-menu callbacks, downloads and history have App handlers, not blanket stubs (`EngineWebContentHostFactory.swift` delegate implementations; `AppSettingsActions.showLibrary`, download actions; App stores). This audit does not claim D/H end-to-end completion. Save Page As currently produces MHTML; that is a real implementation, not a refusal. Crash UI, launch/session preferences, sound effects and engine support gaps need their separate feature audits; they are not missing registry/SidebarIntent/CommandBarIntent handlers.
